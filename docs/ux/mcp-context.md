# Рабочий контекст для MCP-агента

> **Статус: обсуждение, не реализовано; нужна оценка.** См. [обзор раздела](index.md)
> и веб-вариант [session-context.md](session-context.md).

## Вопрос

Полезен ли агенту (пользовательский LLM-агент, подключённый к `/mcp`) серверный
рабочий контекст вроде «работаю с делом X, лист 12» — и сколько токенов он
экономит или тратит.

## Варианты

1. **Без серверного контекста.** Агент держит контекст в своём окне и явно
   передаёт id в каждый вызов. Просто, прозрачно, без скрытого состояния.
2. **Серверная рабочая сессия.** Инструменты `context_set`/`context_get`;
   остальные инструменты берут значения по умолчанию из контекста, если параметр
   опущен. Экономит повторную передачу id, но появляется скрытое состояние:
   агент может забыть, что контекст установлен, и записать данные не туда.
3. **Контекст как подсказка в ответах.** Сервер не подставляет значения, но
   инструменты записи возвращают компактную сводку «текущий контекст: …» и
   кандидатов из него. Без скрытых подстановок, но ответы длиннее.

## Что оценить

- Типовые сессии агента (ввод серии фрагментов из одного дела, построение
  отчёта по персоне): сколько токенов уходит на повторную передачу id и на
  повторные запросы цепочек, в сравнении с накладными расходами варианта.
- Частоту ошибок «не тот контекст» в варианте 2.
- Как контекст сочетается с несколькими параллельными сеансами одного
  владельца (токены, вкладки).
- Можно ли переиспользовать модель слотов веб-контекста (одна модель на оба
  интерфейса).

## Предварительное мнение

Начать с варианта 1 (ничего не делать) и составных инструментов
([assisted-entry.md](assisted-entry.md#составные-сценарии)): они сильнее
экономят вызовы, чем контекст. К варианту 2 или 3 возвращаться по результатам
замеров.
