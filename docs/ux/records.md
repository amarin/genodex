# Структурированные записи документов

> **Статус: обсуждение, не реализовано.** См. [обзор раздела](index.md).

## Идея

Документы известных типов (метрические книги, исповедные ведомости, ревизские
сказки) — это таблицы с устойчивым набором граф. Их выгоднее вводить формой по
типу документа, чем свободным текстом: одна запись формы порождает событие,
персоны, связи и доказательства одним действием. Для новых видов таблиц нужен
**конструктор типов записей**.

Понадобятся две новые сущности:

- **Тип записи** (`RecordType`) — схема: набор граф, их виды, ролевые блоки,
  правила порождения сущностей.
- **Запись** (`Record`) — экземпляр: значения граф конкретной строки документа,
  связанные воедино, с привязкой к месту в источнике.

## Тип записи (RecordType)

- `id`, `name`, `description`, `builtin`, `version`.
- `layout` — форма строки: одиночная запись (метрика), строка таблицы
  с группировкой (исповедная ведомость: двор → члены семьи), разворот с двумя
  сторонами (ревизская сказка: мужской и женский пол).
- `fields[]`:
  - `key`, `label`, `kind` — вид значения: `text`, `given_name`, `patronymic`,
    `surname`, `sex`, `estate`, `place`, `date`, `age`, `number`, `enum`, `note`;
  - `required`, `repeatable` (восприемники, поручители), `group` (ролевой блок);
  - вид графы — одновременно подсказка для извлечения
    ([extraction.md](extraction.md)): в графе «место жительства» ищется топоним.
- **Ролевые блоки** — группы граф, описывающие одного участника:
  «младенец», «отец», «мать», «восприемник», «жених», «невеста», «умерший»,
  «священник». Каждый блок — кандидат в `Person`.
- **Правила порождения** (проекция записи в модель):
  - событие: тип (`birth`, `baptism`, `marriage`, `death`, `burial`, …), какая
    графа — дата, какая — место; участники по ролям (`EventParticipant.Role`);
  - связи между ролями: отец–младенец и мать–младенец → родство, отец–мать →
    супруги (если это следует из документа);
  - факты: сословие (`estate`), проживание (`Residence` с датой записи как
    «упоминается в»), возраст → приблизительный год рождения (`FactDate` с
    `ModifierApprox`).

## Запись (Record)

- `id`, `type_id` + `type_version`.
- `citation_id` — связь 1:1 с `Citation`: запись является структурированной
  формой цитаты. Так цепочка доказательств (`SourceLink → Citation → Source`)
  остаётся прежней, а `ArchiveAnchor` (дело, документ, лист, область) хранится
  в одном месте.
- `number` — номер записи в документе (в метриках — № по мужскому/женскому полу).
- `values[]`: `field_key`, индекс повтора, `raw` (текст как в документе),
  `normalized` (нормализованное значение), `ref` (сущность, если связана).
  Сырой текст графы сохраняется всегда: он — доказательство, нормализация
  на него не влияет.
- `status`: `draft` / `complete` / `verified`.
- Ссылка на пакет изменений, которым созданы порождённые сущности
  ([assisted-entry.md](assisted-entry.md#журнал-пакетов-изменений-и-отмена)).

Хранение — нормализованные таблицы (`records`, `record_values`, `record_types`,
`record_type_fields`), по аналогии с остальной схемой, с поисковыми терминами
по значениям граф.

## Проекция и подтверждение

1. Пользователь заполняет форму (с предзаполнением из контекста и предыдущей
   записи).
2. Система строит **предложения**: для каждого ролевого блока — «новая
   персона» или кандидаты из базы; события, связи, факты; места — связывание
   с `AdministrativeDivision`.
3. Пользователь подтверждает (по умолчанию: места и словарные значения приняты,
   персоны — «новая» или выбранный кандидат явно).
4. Создание одной транзакцией (`InTx`) с `SourceLink` на цитату записи
   (`Role` = роль/графа).

**Правка записи после подтверждения.** Подтверждённые сущности независимы и
автоматически не меняются. Система пересчитывает проекцию, сравнивает
с созданным и предлагает изменения: «в записи исправлено отчество отца —
обновить персону?».

## Встроенные типы

Хранятся во встроенных данных (`internal/definitions`), по образцу
административного деления; пользователь может скопировать встроенный тип и
изменить копию.

- **Метрическая книга, ч. 1 — о родившихся:** №, даты рождения и крещения,
  имя младенца, пол, родители (звание, имя, отчество, фамилия,
  вероисповедание), восприемники (повторяемый блок), кто совершал таинство.
- **Метрическая книга, ч. 2 — о бракосочетавшихся:** №, дата, жених и невеста
  (звание, имя, отчество, фамилия, вероисповедание, какой брак, лета),
  поручители по жениху и по невесте, кто совершал таинство.
- **Метрическая книга, ч. 3 — об умерших:** №, даты смерти и погребения,
  звание, имя, отчество, фамилия, лета, причина смерти, кто исповедовал и
  причащал, кто совершал погребение, где погребён.
- **Исповедная ведомость:** № двора, члены семьи с отношением к главе,
  лета мужского и женского пола, отметки об исповеди и причастии, причины
  неявки. Таблица, группировка по двору.
- **Ревизская сказка:** двор/семья; мужской пол (лета по прошлой ревизии,
  выбыл — когда и почему, лета ныне); женский пол (лета ныне). Разворот из двух
  сторон; формы ревизий 1–10 различаются.

Формы бланков менялись по годам и епархиям — встроенный тип либо допускает
необязательные графы, либо имеет варианты (решить при обсуждении).

## Конструктор типов

- UI описания новой таблицы: графы, их виды, ролевые блоки, повторяемость.
- **Этап 1:** только графы и виды — запись хранится структурированно,
  виды граф служат подсказками извлечению, порождения сущностей нет.
- **Этап 2:** правила порождения (события, связи, факты) в конструкторе —
  простой визуальный набор правил, без языка выражений.
- **Версии типа.** Добавление графы безопасно. Удаление или переименование
  при существующих записях — новая версия типа; старые записи остаются на
  своей версии или мигрируются явно.

## Рабочее место ввода документа

- Слева — скан (`Attachment`): масштаб, выделение области → `ArchiveAnchor.Rect`
  (позже — область на каждую графу).
- Справа — форма записи по выбранному типу; контекст (дело, документ, лист)
  закреплён ([session-context.md](session-context.md)).
- Автоинкремент номера записи и листа; переход «следующий лист / оборот».
- Копирование значений из предыдущей записи (тот же священник, та же деревня)
  одной клавишей; ввод без мыши (Tab по графам, Enter — сохранить и следующая).
- Под формой — список записей текущего листа.

## Сложности

- **Нечитаемое и исправления в источнике:** отметки `[неразборчиво]`,
  зачёркнутое, приписки на полях — нужны отдельные виды пометок в `raw`,
  а не потеря информации.
- **Даты** — юлианский календарь (`FactCalendarJulian`), даты без года
  (год из документа), «того же месяца».
- **Одна запись на несколько листов** и несколько записей на одной цитате.
- **Семья в ревизской сказке и исповедной ведомости** — связи «жена», «сын»,
  «сноха» задаются относительно главы двора, а не соседней строки.
- **Производительность ввода** важнее полноты: форма не должна требовать
  заполнения всего, неполная запись — нормальная (`draft`).

## Открытые вопросы

- Всегда ли 1:1 `Record ↔ Citation`, и что тогда в `Citation.Text`:
  полная расшифровка строки или генерируемое представление граф.
- Варианты встроенных типов или необязательные графы.
- Язык правил порождения для пользовательских типов (этап 2).
- Нужна ли область на скане для каждой графы.
