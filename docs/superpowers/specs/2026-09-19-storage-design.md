## Контекст и проблема

Текущий сервис (`genodex`) держит данные в in-memory хранилище (`internal/store/store.go`),
а связанные сущности (персоны, места, события, источники, архивная цепочка) описывает
в документе `docs/data-model.md`. Реальный набор данных накоплен в Obsidian-волте
(`/Users/asmarin/Documents/MD`): ~530 персон, ~3500 markdown-файлов архивных дел,
~250 адм. единиц, словари, плюс ~9 GB медиа (сканы, аудио).

Обсуждение выявило цели и ограничения:

1. **Markdown не самоцель.** Волт — одноразовый источник для импорта («бутстрап»),
   а не живой источник истины. Ручные правки markdown после импорта не поддерживаются.
   Внутренний формат хранения — собственный.
2. **Пользователь не должен испытывать затруднений при запуске** и не нуждается в
   дополнительных зависимостях: один бинарник, без внешних СУБД и без cgo.
3. **Гибкий поиск по связям** — ядро сценария использования: «все крестьяне в губернии N,
   уезде M», «все документы с упоминанием персоны X» и т. п. Индексы на все отношения
   (o2o, o2m, m2m) создаются при добавлении сущности; связывание упоминаний — асинхронно.
4. **Версионируемая история правок**: восстановление полного состояния по журналу,
   даже при потере самой базы.
5. **Медиа (изображения, аудио) не должны попадать в RDB** — только метаданные;
   файлы остаются на диске.
6. **Бэкап без остановки программы** и навязываемый «правильный паттерн» резервирования.

## Решение

Гибрид:

- **SQLite** (`modernc.org/sqlite`, pure-Go, без cgo) — транзакционное ядро для
  структурированных данных и индексов. Все штатные механизмы SQLite (WAL,
  foreign keys, crash-recovery) остаются включёнными и используются.
- **Внешний append-only журнал** (`journal.jsonl`) — страховка и постоянно пополняемый
  непрерывный бэкап. Не заменяет внутреннюю консистентность SQLite, а дублирует поверх.
- **Медиа — файлы на диске**; в БД только метаданные (`attachment`: path, sha256, mime, size).
- **Заметки — markdown TEXT в БД** (небольшое форматирование; отдельные .md-файлы не нужны).
- **Импорт**: одноразовый, отдельным процессом, со строгой проверкой и карантином
  непрошедших документов (не молчаливым отбрасыванием).
- **Бэкап на лету**: `VACUUM INTO` даёт консистентный снапшот без остановки.
  Паттерн пользователя: «забудьте про `.db`, бэкапьте только `backup/` + медиа-каталог».

## Размеры (оценка по текущему волту)

| Компонент | Оценка |
|---|---|
| Данные: текст (персоны, фрагменты, места, словари) | ~12 MB |
| Индексы нормализации (`*_norm` + B-tree) | ~4 MB |
| Рёбра отношений (Residence/Relation/упоминания, ~10–15 тыс.) | ~1–3 MB |
| SQLite overhead (страницы, схема, ~1.5×) | — |
| **Итого БД** | **~20–40 MB** |
| Журнал (накопленный за ~2 года, полные образы, ~2.5 КБ/запись) | ~25–60 MB |
| Рост журнала при активной работе | ~10–30 MB/год |
| Медиа (в БД не попадают; метаданные ~1600 строк × ~200 B) | ~0.3 MB / 8.5 GB файлов |

Журнал растёт с числом правок, а не сущностей: каждая правка пишет полный объект.

## Архитектура потока записи

```
правка ──► 1) journal.jsonl: append + fsync        (инвариант: журнал не младше БД)
        ──► 2) SQLite: BEGIN; UPDATE/INSERT; COMMIT (WAL fsync)
                     │
    genodex backup (по расписанию / по команде):
        VACUUM INTO snapshot.db
        + записать в журнал маркер (op:"snapshot", seq)
        + манифест (sha256, счётчики, версия схемы)
                     │
    genodex restore:
        открыть snapshot.db → replay журнала с seq > маркера → integrity_check
        → сверить счётчики с манифестом
```

Инвариант: **журнал никогда не младше БД**. При крахе в окне между шагами 1 и 2 БД
просто отстаёт на последнюю операцию и догоняется из журнала при старте.

- Полные после-образы (не дифы) → replay идемпотентен и не требует merge.
- Запись журнала: `{"seq":N, "op":"save|delete|snapshot", "entity":"person", "id":"...", "at":"RFC3339", "payload":{...}}`.
- `seq` — монотонный номер; маркер `op:"snapshot"` фиксирует, откуда replay начинается.

## Схема данных (SQLite)

Схема отражает модели из `docs/data-model.md` как есть; здесь фиксируются только
сквозные принципы, общие для всех таблиц сущностей.

### Сущностные таблицы

- Одна таблица на тип сущности (`person`, `administrative_division`, `event`, `source`,
  `archive_node`, `attachment`, ...) либо общая таблица с типом — реализация уточнит.
- Первичный ключ — строковый `id` из модели (формат `ПРЕФИКС-ULID`, см.
  `docs/data-model/identifiers.md`; правило «транслит + дисамбигуатор» отменено).
- JSON-поля модели, которые в реляционной форме не разворачиваются (например,
  вложенные `PersonName[]`, `TextRef[]`, вложенные блоки заметок) — **как JSON в TEXT**.
- **Заметки (markdown)** — TEXT-колонки `note`/`body`, рендерятся на фронте.

### Нормализация для кириллицы

SQLite `NOCASE` — ASCII-only; сортировка/поиск не отдаётся СУБД.

- У каждой атрибутной колонки, по которой ищется/сортируется текст, есть парная
  `*_norm` колонка: `name` → `name_norm`.
- Нормализация в одном Go-месте (используется и при записи, и при запросе):
  `strings.ToLower` → `ё→е` → NFD (golang.org/x/text/unicode/norm) → убрать
  диакритику/комбинирующиеся символы по мере необходимости.
- Поиск идёт по `name_norm = ?` / `name_norm LIKE 'сем%'` (значение нормализуется
  перед подстановкой). B-tree индекс на `*_norm`.
- Это же решает Семенов/Семёнов и транслит-варианты.

### Отношения и индексы

- Связи o2o/o2m/m2m — таблицы рёбер с FK (`relation`, `residence`, `event_participant`,
  `source_link`, `attachment_ref`, ...).
- Для фильтров вида «крестьяне в губернии N, уезде M» — **денормализованный путь
  иерархии**: в каждой `residence` хранится список ancestor-идентификаторов
  (`[губерния, уезд, волость, ...]`). Фильтр = пересечение множеств id.
- Упоминания персоны в тексте фрагмента — рёбра `mention(entity_a, entity_b)`; создаются
  при добавлении сущности: scan корпуса по нормализованным вариантам имени → найденные
  фрагменты → рёбра. **Единственная дорогая операция, выполняется асинхронно.**
  Всё остальное индексируется синхронно при записи.

### Медиа

- Таблица `attachment(id, entity_ref, path, sha256, mime, size)`.
- Файлы — на диске, в каталоге по сущности. В БД — только строки метаданных.
- Атомарность: сначала файл (temp → rename), потом строка в БД; осиротевшие файлы
  подчищаются при старте.
- `verify` сверяет `sha256` ожидаемого в БД с фактическим файлом.

## Бэкап / восстановление (паттерн пользователя)

Паттерн встраивается в продукт, а не только в README:

- Каталоги: `db/` (БД + журнал) и `backup/` — раздельно;
  при старте **sentinel**: если `db/` и `backup/` на одном устройстве — предупреждение
  «бэкап на том же диске не спасает от отказа диска».
- **`genodex backup [--to <dir>]`**: `VACUUM INTO snapshot.db` + хвост журнала +
  `manifest.json` (версия схемы, sha256 снапшота и журнала, счётчики сущностей).
  Манифест пишется последним.
- **`genodex restore --from <dir>`**: в новую директорию; `PRAGMA integrity_check` →
  replay журнала → повторная проверка счётчиков из манифеста. Поверх живых данных —
  только с `--force`.
- **`genodex verify`**: целостность БД + сверка медиа по sha256 + сверка БД с журналом.
- **Авто-бэкап**: при чистом shutdown и раз в сутки (дёшево), удержание последних N бандлов.
- Пользователь бэкапит только `backup/` + медиа-каталог (внешним инструментом);
  восстановление = `restore` бандла → восстановление медиа-каталога → `verify`.

## Импорт из волта (одноразовый)

- Отдельный процесс: `genodex import --vault <path>` с явными параметрами.
- Строгая проверка формата (frontmatter + структура папок по `genealogy-router`).
- **Не** молчаливое отбрасывание: непрошедшие документы → карантин
  (`import-errors/`) + отчёт с причинами. Пользователь решает: починить/пожертвовать.
- Импорт пишет в БД и в журнал штатным путём (каждая операция — запись журнала).
