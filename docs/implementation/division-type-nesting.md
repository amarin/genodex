# Вложенность типов административного деления

## Задача

В форме добавления дочерней единицы список типов содержал все типы — в село
можно было добавить губернию. Фильтр в UI защищал только веб-интерфейс:
MCP-ассистент и прямые вызовы `/api` могли создать губернию в уезде. Правила
перенесены на сервер, UI получает их справочником.

## Правило

Ранг типа — условная «высота» в иерархии (`models.adminDivisionTypeRanks`);
`models.AdminDivisionType.CanContain(child)` — ранг ребёнка строго ниже
родителя. Единицы деления всегда выше населённых пунктов; типы одного уровня
разных систем деления (губерния/область/наместничество/край, уезд/район,
волость/сельсовет) равны — смешение систем допустимо, «вверх» — нет.
`other` ранга не имеет: внутрь него — любой тип; само оно — в любой единице
деления, но не в населённом пункте. Значения рангов — в `docs/models/places.md`.

Существующие данные (`.data`, 409 связей на 2026-09-24) правилу
соответствуют, миграция не нужна.

## Сервер

- `models`: `AdminDivisionType.Rank`, `CanContain`, `AllowedChildTypes`,
  `Label` (русский термин), `AdminDivisionTypeInfo` + `AdminDivisionTypeInfos`
  (справочник), `NestingError` — `*ValidationError` с перечнем допустимых
  дочерних типов (по нему MCP-ассистент исправляет вызов).
- `usecases/create_division`: после чтения родителя — `NestingError` по полю
  `type`.
- `usecases/update_division`: `checkNesting` — только при смене типа или
  родителя (правка названия у записи, сохранённой до правил, не ломается).
  Новый родитель должен допускать тип (поле `parent_id`; при неизменном
  родителе — `type`); новый тип должен допускать типы всех текущих детей
  (`ChildrenOfDivision` окнами по `MaxPageLimit`, поле `type`).
- `usecases/list_division_types`: справочник без зависимостей; фасад
  `divisionService.ListDivisionTypes` в `internal/app`.
- HTTP: `GET /api/admin-division-types` → `[]transport.AdminDivisionTypeInfo`
  (`type`, `label`, `rank`, `settlement`, `children`). Нарушение
  вложенности при записи — `422` с `field`.
- MCP: тул `division_type_list`; в описаниях `division_create` /
  `division_update` — правило вложенности и требование «name — только имя
  собственное».

Проверка «слово-тип в названии» на сервер **не** перенесена: в данных есть
село «Погост» — имя собственное, совпадающее с термином.

## Веб

- `web/src/divisionTypes.ts`: `useAdminDivisionTypes` (справочник, один
  запрос на страницу — кеш в `fetchAdminDivisionTypes`), `allowedChildTypes`
  по справочнику (не загружен — без фильтра, сервер всё равно проверит),
  `childKinds`/`childKindsPhrase` для подписей, `typeWordInName` и правила
  поля «Название».
- `CreateDivisionModal` (`parentType`): список типов фильтруется; заголовок —
  «Добавить деление или населённый пункт» / «Добавить населённый пункт» /
  «Добавить деление»; плейсхолдер «название, без типа»; слово-тип в
  названии — предупреждение (`warningOnly`: термин бывает именем
  собственным, село «Погост»); «Создать» неактивна, пока название пустое
  или тип не выбран.
- `DivisionView`: кнопка «+ деление или населённый пункт» / «+ населённый
  пункт» / «+ деление», скрыта, если добавить нечего (хутор). В форме
  редактирования — то же предупреждение о слове-типе.
- Навигация: шапка «Генеалогия · Данные · Справочники»; каталог сущностей
  (`/`) называется «Данные» (и в хлебных крошках); раздел «Справочники»
  (`/reference`, `ReferenceCatalog`) со страницей
  `/reference/division-types` (`DivisionTypesPage`, только чтение).

## Не сделано

Ранги не редактируются из интерфейса: набор типов закрыт в коде, новый тип
всё равно требует правки кода, а хранимые ранги потребовали бы таблицы в
схеме и решения о записях, ставших «неправильными» после смены рангов.
