# Рандеву и поиск узлов по идентичности

Проектный документ. Описывает децентрализованный механизм, с помощью которого два экземпляра приложения находят друг друга и устанавливают соединение, зная только криптографическую идентичность собеседника, а не его сетевой адрес.

Документ **не привязан к genodex**. Описанный сервис самодостаточен и может быть реализован как отдельная библиотека или демон и встроен в любой продукт, которому нужна такая функциональность. Прикладной обмен данными (что именно передаётся после установления соединения) за пределами этого документа.

## 1. Назначение и границы

### Что решает

- **Поиск по идентичности.** Узел A хочет соединиться с узлом B, зная публичный ключ B, но не зная его адрес.
- **Взаимное согласие.** Соединение возможно только между узлами, которые ранее явно подтвердили друг друга. Односторонний «звонок» незнакомцу невозможен по построению.
- **Проход через NAT.** Большинство узлов не имеют прямой доступности извне.
- **Отсутствие центра.** Нет единой точки регистрации, авторизации или владения именами.

### Исходные ограничения

1. Система полностью децентрализованная.
2. Для работы сети нужен хотя бы один условно-постоянный координатор. Нет доступных координаторов — нет подключения.
3. Любой узел с прямой доступностью извне (проброс порта, UPnP, публичный IP) может стать координатором.

### Чего система не делает

- Не хранит прикладные данные и не разрешает конфликты синхронизации.
- Не даёт глобальных человекочитаемых имён. Идентификатор — ключ; отображаемое имя локально и задаётся владельцем адресной книги.
- Не гарантирует анонимность на уровне I2P или Tor. Цель — минимизация метаданных, а не сокрытие факта участия в сети.
- Не обеспечивает доставку при отсутствии координаторов.

## 2. Роли и термины

| Термин | Значение |
|---|---|
| **Узел (node)** | Экземпляр приложения. Идентифицируется долговременной ключевой парой. |
| **NodeID** | Публичный ключ узла (или его хеш). Единственный постоянный идентификатор. |
| **Клиент** | Узел в обычном режиме: исходящие соединения, за NAT, нестабильный адрес. |
| **Координатор** | Узел с прямой доступностью, дополнительно выполняющий функции справочника, точки встречи и ретранслятора. Координатор — это режим работы, а не отдельный продукт. |
| **Домашние координаторы** | 2–3 координатора, с которыми узел держит постоянное соединение и на которых публикует свою запись. |
| **Контакт** | Другой узел, с которым установлено взаимное доверие. |
| **Карточка контакта** | Подписанный набор: NodeID + подсказки, где искать узел. Передаётся при знакомстве. |
| **Токен встречи (rendezvous token)** | Непрозрачная для координатора метка, которую могут вычислить только два конкретных контакта. |
| **Реле (relay)** | Передача трафика через координатора, когда прямое соединение не удалось. |

## 3. Слои системы

Снизу вверх. Каждый слой опирается на нижний и не знает о верхних.

| № | Слой | Содержание | Обязателен |
|---|---|---|---|
| L0 | Транспорт | TCP/QUIC, шифрование и аутентификация по ключам узлов | да |
| L1 | Идентичность | ключевые пары, отпечатки, подписи записей | да |
| L2 | Вход в сеть (bootstrap) | кэш координаторов, seed-список, приглашения, mDNS | да |
| L3 | Справочник (directory) | публикация и поиск записей о доступности узла | да |
| L4 | Рандеву и NAT traversal | сведение сторон, hole punching, реле | да |
| L5 | Доверие и согласие | приглашения, сверка отпечатков, списки доверенных | да |
| L6 | Приватность | токены встречи вместо открытых записей | желательно |
| L7 | Асинхронность | почтовый ящик на координаторе | опционально |
| L8 | Масштабирование | DHT среди координаторов вместо полной репликации | по мере роста |

## Часть I. Координатор

### I.1. Функции

Координатор — узел без прикладной логики и без доступа к содержимому прикладного обмена. Пять функций:

1. **Справочник (directory).** Принимает от узлов подписанные записи о доступности и отдаёт их по запросу.
2. **Точка встречи (rendezvous).** Сводит два узла, одновременно заявивших об интересе к одной встрече, и передаёт им сведения друг о друге для прямого соединения.
3. **Сигнализация NAT traversal.** Сообщает узлу его внешний адрес и координирует одновременные попытки соединения с обеих сторон.
4. **Реле.** Передаёт зашифрованный поток между двумя узлами, когда прямое соединение не установилось. Объём и длительность ограничены квотами.
5. **Участие в сети координаторов.** Обмен с другими координаторами списками координаторов и (при необходимости) записями узлов.

Опционально: **почтовый ящик** — временное хранение зашифрованных сообщений для узла, который сейчас офлайн.

### I.2. Состояние

Всё состояние координатора эфемерно и восстановимо. Потеря состояния приводит к переподключению узлов, но не к потере данных.

| Таблица | Содержание | TTL |
|---|---|---|
| Сессии | активные соединения узлов, их внешние адреса | время жизни соединения |
| Записи доступности | подписанные анонсы узлов | минуты–часы |
| Ожидающие встречи | токен встречи → сессия ожидающего | минуты |
| Известные координаторы | адрес, время последнего успешного контакта, возраст | часы–сутки |
| Почтовые ящики | зашифрованные сообщения по адресату | сутки, лимит объёма |
| Квоты | счётчики по сессиям и IP | окно |

### I.3. Сценарии (взгляд координатора)

**C1. Узел подключился.** Устанавливается защищённая сессия, координатор узнаёт NodeID собеседника и его внешний адрес, создаёт запись сессии. Отдаёт узлу его внешний адрес (как он виден снаружи) и текущий список известных координаторов.

**C2. Узел публикует запись доступности.** Координатор проверяет подпись и соответствие NodeID сессии, проверяет свежесть (счётчик `seq` не должен убывать), сохраняет с TTL. Открытая запись — для публичного режима; в приватном режиме вместо неё публикуется токен встречи (см. C4).

**C3. Узел ищет другой узел по NodeID.** Координатор отдаёт сохранённую запись, если она есть и не протухла. Если записи нет — отвечает «не знаю» и, в режиме с DHT (D8), может переадресовать запрос ближайшим по ключу координаторам.

**C4. Две стороны заявили один токен встречи.** Координатор не знает, кто эти узлы и почему их токены совпали. Он сопоставляет токены, и если обе стороны сейчас в сети — переходит к сведению (C5). Если пришёл только один — токен ждёт в таблице до истечения TTL.

**C5. Сведение сторон.** Координатор сообщает каждой стороне внешние адреса другой (несколько кандидатов: внешний, локальные) и общее время старта попытки. Обе стороны одновременно инициируют соединение навстречу — это и есть hole punching. Координатор не участвует в проверке подлинности сторон: они аутентифицируют друг друга сами на рукопожатии.

**C6. Прямое соединение не удалось — запрос реле.** Координатор проверяет квоты и, если позволяет политика, открывает двунаправленный туннель между двумя сессиями. Содержимое зашифровано между конечными узлами; координатор видит только объём и длительность.

**C7. Узел просит проверить свою доступность.** Координатор пытается установить входящее соединение на заявленный узлом адрес. Результат («снаружи достижим / недостижим») возвращается узлу. Это основа решения узла о переходе в режим координатора. Аналог — [AutoNAT в libp2p](https://github.com/libp2p/specs/tree/master/autonat).

**C8. Узел анонсирует себя как координатора.** Координатор принимает анонс, только если сам успешно проверил доступность узла (C7) либо получил подтверждение от другого координатора. Новый координатор попадает в список известных и начинает распространяться по сети.

**C9. Обмен с другим координатором (gossip).** Периодически: обмен списками известных координаторов, отсев недоступных, обновление времени последнего контакта. При включённом DHT — также обмен записями в зоне ответственности.

**C10. Приём сообщения в почтовый ящик.** Координатор принимает зашифрованный блоб с адресом-получателем (токеном), сохраняет с TTL и лимитом объёма. Отдаёт адресату при его подключении; после подтверждённой выдачи удаляет.

**C11. Обслуживание квот и уборка.** Удаление протухших записей, ограничение частоты запросов, ограничение числа записей на одну сессию, ограничение трафика реле.

### I.4. Что координатор принципиально не может

Это границы доверия; они определяют, что можно доверить произвольному узлу в роли координатора.

- **Прочитать прикладной обмен.** Шифрование сквозное, между конечными узлами.
- **Подделать запись узла.** Записи подписаны ключом узла.
- **Выдать себя за узел.** Рукопожатие сторон проверяет ключи напрямую.
- **Связать токен встречи с личностями.** Токен выводится из секрета, известного только двум контактам.

Что координатор может и чему нужно противодействовать на стороне клиента:

- **Отказать в обслуживании или скрыть запись.** Противодействие: несколько домашних координаторов из независимых источников.
- **Подменить список координаторов** (eclipse-атака). Противодействие: не вытеснять проверенные записи кэша новыми, брать координаторов из разных источников.
- **Наблюдать метаданные**: какие IP подключены, когда, сколько трафика. Противодействие: токены встречи, ограничение публикуемой информации, при высоких требованиях — транспорт поверх анонимизирующей сети.

## Часть II. Клиент

### II.1. Сценарии

**U1. Первый запуск.** Узел генерирует ключевую пару, сохраняет её в локальном хранилище, показывает пользователю свой отпечаток и пустую адресную книгу. В сеть пока не входит.

**U2. Вход в сеть (bootstrap).** По порядку, до первого успеха:
1. локальный кэш координаторов (самый частый путь после первого запуска);
2. координаторы из карточек известных контактов;
3. seed-список из конфигурации или поставки;
4. mDNS в локальной сети.

Ни один способ не сработал — вход в сеть невозможен, узел сообщает об этом пользователю и повторяет попытки с нарастающим интервалом.

**U3. Выбор домашних координаторов.** Узел выбирает 2–3 из доступных, предпочитая давно и стабильно отвечающих и по возможности из разных источников. Держит с ними постоянное соединение, переподключается при разрыве.

**U4. Публикация своей доступности.** В публичном режиме — подписанная запись `NodeID → адреса или «через координатора X»`. В приватном режиме (по умолчанию) — только токены встречи для контактов из адресной книги, на текущую эпоху.

**U5. Приглашение контакта.** Пользователь A создаёт приглашение: карточку с NodeID, списком домашних координаторов, одноразовым секретом и сроком действия. Передаёт её любым внешним каналом (QR, ссылка, мессенджер).

**U6. Принятие приглашения.** B находит A по карточке, предъявляет одноразовый секрет, стороны обмениваются ключами. Оба клиента показывают короткий отпечаток; пользователи сверяют его по независимому каналу (голосом, лично). После подтверждения обеими сторонами ключи заносятся в списки доверенных. Это и есть момент взаимного согласия.

**U7. Соединение с контактом.** По порядку, до первого успеха:
1. последний известный адрес из кэша;
2. токен встречи на домашних координаторах контакта (из его карточки);
3. токен встречи на собственных домашних координаторах;
4. поиск через сеть координаторов (gossip или DHT) — запасной вариант, если все координаторы контакта исчезли.

Далее: рукопожатие с проверкой ключа по списку доверенных, при неудаче прямого соединения — hole punching, затем реле.

**U8. Приём входящего соединения.** Ключ инициатора проверяется по списку доверенных до передачи любых прикладных данных. Ключа нет в списке — соединение закрывается. Никаких «запросов на добавление в друзья» по сети: добавление возможно только через приглашение (U5/U6).

**U9. Смена координаторов или адреса.** Узел публикует обновлённую карточку с увеличенным `seq` и **рассылает её контактам**, с которыми сейчас на связи. Так подсказки в адресных книгах контактов остаются актуальными без глобального реестра.

**U10. Переход в режим координатора.** Узел проверяет внешнюю доступность (UPnP/NAT-PMP или ручной проброс), просит 2–3 разных координатора подтвердить доступность (C7), выдерживает порог по времени непрерывной работы и только затем анонсирует себя (C8). Пользователь может запретить этот режим настройкой.

**U11. Контакт офлайн.** Если включён почтовый ящик — узел оставляет зашифрованное сообщение на домашних координаторах контакта. Иначе — сообщает пользователю о недоступности и повторяет попытки по расписанию.

**U12. Отзыв доверия.** Удаление ключа из списка доверенных. Прекращается публикация токенов встречи для этого контакта; входящие соединения с этим ключом отклоняются. Уже переданные данные не отзываются.

**U13. Смена ключа или потеря устройства.** Узел с новым ключом рассылает контактам сообщение о смене, подписанное **старым** ключом (если тот доступен). При утрате старого ключа знакомство проходит заново через U5/U6.

### II.2. Локальное состояние клиента

| Хранилище | Содержание |
|---|---|
| Ключи | долговременная ключевая пара; приватный ключ под защитой ОС или пароля |
| Адресная книга | контакты: NodeID, локальное имя, статус сверки отпечатка, общий секрет, подсказки-координаторы, последний известный адрес |
| Кэш координаторов | адрес, ключ, время последнего успеха, накопленная надёжность |
| Приглашения | выданные и ещё не использованные, со сроками |
| Настройки | режим координатора, лимиты реле, приватный/публичный режим публикации |

## Часть III. Детализация

Блоки ниже фиксируют выбор технологий и форматов. Для стандартных вещей даны ссылки на внешние спецификации, повторять их содержание не нужно.

### D1. Идентичность и криптография

- **Ключи узла**: Ed25519 для подписей — [RFC 8032](https://www.rfc-editor.org/rfc/rfc8032). NodeID — публичный ключ или его хеш в компактном представлении (base32 без разделителей).
- **Согласование общего секрета** контактов: X25519 — [RFC 7748](https://www.rfc-editor.org/rfc/rfc7748). Из него выводятся ключи токенов встречи через HKDF — [RFC 5869](https://www.rfc-editor.org/rfc/rfc5869).
- **Транспортное рукопожатие**: [Noise Protocol Framework](https://noiseprotocol.org/noise.html), паттерн `XX` (обе стороны узнают ключ друг друга в процессе) или `IK`, если ключ собеседника известен заранее. Альтернатива — TLS 1.3 с закреплением ключей (raw public keys, [RFC 7250](https://www.rfc-editor.org/rfc/rfc7250)).
- **Отпечаток для сверки людьми**: хеш обоих публичных ключей, отображаемый как числовой код или набор слов. Подход описан в [Signal safety numbers](https://signal.org/blog/safety-number-updates/).
- **Транспорт**: QUIC ([RFC 9000](https://www.rfc-editor.org/rfc/rfc9000)) предпочтителен — мультиплексирование и лучшее прохождение NAT по UDP; TCP как запасной.

### D2. Форматы записей

Все записи — подписанные структуры с обязательными полями `seq` (монотонный счётчик) и `expires`. Кодирование: CBOR или protobuf; конкретный выбор не принципиален, важна каноничность представления перед подписью.

**Карточка контакта** (передаётся при знакомстве, встраивается в ссылку или QR):

```
ContactCard {
  node_id            // публичный ключ
  hints[]            // адреса домашних координаторов
  invite_secret?     // одноразовый, только в приглашении
  expires
  seq
  signature
}
```

**Запись доступности** (публичный режим, публикуется на координаторе):

```
Presence {
  node_id
  addrs[]            // прямые адреса, если есть
  via[]              // координаторы, через которых доступен
  seq, expires
  signature
}
```

**Заявка на встречу** (приватный режим):

```
RendezvousClaim {
  token              // непрозрачен для координатора, см. D6
  session_pubkey     // эфемерный ключ для этой встречи
  expires
}
```

### D3. Поверхность API координатора

Логические операции; конкретный вид (RPC поверх мультиплексированного соединения) — деталь реализации.

| Операция | Направление | Назначение |
|---|---|---|
| `hello` | клиент → координатор | установление сессии, возврат внешнего адреса и списка координаторов |
| `publish` | клиент → координатор | публикация `Presence` |
| `lookup` | клиент → координатор | поиск по NodeID |
| `claim` | клиент → координатор | заявка на встречу по токену |
| `connect-notify` | координатор → клиент | уведомление о встречном узле, кандидаты адресов, время старта |
| `relay-open` | клиент → координатор | запрос реле |
| `probe` | клиент → координатор | проверка внешней доступности (C7) |
| `announce-coordinator` | клиент → координатор | заявка на роль координатора |
| `peers-exchange` | координатор ↔ координатор | gossip списков координаторов |
| `mailbox-put` / `mailbox-get` | клиент ↔ координатор | почтовый ящик |

### D4. Прохождение NAT

Ничего нового изобретать не нужно, механика отраслевая:

- Определение внешнего адреса — STUN, [RFC 8489](https://www.rfc-editor.org/rfc/rfc8489). В нашей схеме роль STUN-сервера играет координатор в рамках `hello`.
- Перебор кандидатов адресов и выбор рабочей пары — ICE, [RFC 8445](https://www.rfc-editor.org/rfc/rfc8445). Для простоты допустима упрощённая схема: несколько кандидатов и одновременный старт с обеих сторон.
- Одновременное открытие соединения через координатора-сигнализатора — [DCUtR в libp2p](https://github.com/libp2p/specs/blob/master/relay/DCUtR.md).
- Реле — [Circuit Relay v2](https://github.com/libp2p/specs/blob/master/relay/circuit-v2.md); отраслевой аналог TURN, [RFC 8656](https://www.rfc-editor.org/rfc/rfc8656).
- Проброс порта на домашнем маршрутизаторе — UPnP IGD или NAT-PMP/PCP, [RFC 6887](https://www.rfc-editor.org/rfc/rfc6887).
- Проверка реальной внешней доступности — [AutoNAT](https://github.com/libp2p/specs/tree/master/autonat). Успех UPnP сам по себе доступность не доказывает.

Симметричный NAT с обеих сторон hole punching обычно не проходит — для таких пар реле остаётся единственным вариантом. Это нормальная доля, её нужно закладывать в расчёт нагрузки координаторов.

### D5. Вход в сеть и распространение списка координаторов

- Кэш координаторов с оценкой надёжности: аналог `peers.dat` и сообщений `addr` в Bitcoin — [описание P2P-сети](https://developer.bitcoin.org/devguide/p2p_network.html).
- Локальная сеть: mDNS / DNS-SD, [RFC 6762](https://www.rfc-editor.org/rfc/rfc6762), [RFC 6763](https://www.rfc-editor.org/rfc/rfc6763).
- Распространение — эпидемический обмен (gossip): при каждом контакте стороны обмениваются небольшой случайной выборкой известных координаторов. Это даёт быстрое распространение без централизации.
- **Защита от eclipse**: новые записи не вытесняют проверенные; кэш разделён на «проверенные» и «новые» с ограничением по подсетям. Разбор подхода — [статья об eclipse-атаках на Bitcoin](https://www.usenix.org/conference/usenixsecurity15/technical-sessions/presentation/heilman).

### D6. Токены встречи (приватный режим)

Цель: координатор сводит стороны, не зная, кого именно сводит.

1. При знакомстве A и B выводят общий секрет `S` (X25519 + HKDF).
2. Время делится на эпохи (например, сутки, с перекрытием на границе).
3. Обе стороны вычисляют `token = HMAC(S, epoch || salt)` и публикуют его на координаторах.
4. Координатор видит два совпавших непрозрачных значения и сводит стороны (C4/C5).

Свойства: посторонний не может вычислить токен, не зная `S`; токены разных эпох не связываются между собой; координатор не узнаёт NodeID участников. Родственные механизмы — [ослеплённые ключи onion-сервисов Tor v3](https://spec.torproject.org/rend-spec-v3.html) и модель контактов в [Briar](https://code.briarproject.org/briar/briar/-/wikis/home).

Компромисс: публичный режим (открытая `Presence`) проще в отладке и позволяет находить узел без предварительного знакомства; приватный режим сильно снижает утечку метаданных. Режим выбирается настройкой; по умолчанию приватный.

### D7. Почтовый ящик (опционально)

Нужен, только если требуется работа при неодновременном присутствии сторон. Координатор хранит непрозрачные блобы, адресованные токену получателя, с жёстким TTL и квотой на отправителя. Ящик не даёт гарантий доставки и не является транспортом для больших объёмов — только для коротких уведомлений вида «есть обновления, соединись со мной».

### D8. Масштабирование справочника

Пока координаторов десятки, каждый может хранить полный набор записей. При росте — переход на Kademlia **только среди координаторов**; обычные клиенты остаются потребителями:

- [Оригинальная работа по Kademlia](https://pdos.csail.mit.edu/~petar/papers/maymounkov-kademlia-lncs.pdf);
- практическая спецификация — [BEP-5 (BitTorrent DHT)](https://www.bittorrent.org/beps/bep_0005.html);
- реализация с готовыми режимами server/client — [libp2p Kad-DHT](https://github.com/libp2p/specs/tree/master/kad-dht);
- двухуровневая модель «сильных» узлов, хранящих справочник, — [netDb и floodfill в I2P](https://geti2p.net/en/docs/how/network-database).

Порог перехода определяется эксплуатационно: когда полный обмен записями между координаторами начинает заметно нагружать сеть.

### D9. Выбор реализации — решено 2026-09-23 (задача F9)

Главное решение здесь — **не выбирать сейчас, а изолировать**.

Прикладной протокол (пакеты, подписки, курсоры, отзывы) работает поверх одной
абстракции: **поток байт между двумя аутентифицированными узлами**. Ниже этой
линии транспорт заменяется, не задевая ничего выше.

**Честное сравнение.** go-libp2p даёт транспорты, шифрование, мультиплексирование,
Kad-DHT, AutoNAT, Circuit Relay v2, DCUtR, mDNS. Но DHT мы решили не делать до
появления надобности, а **протокол координатора пишем сами в любом случае** —
анонсы, точки встречи, реле с нашими квотами, почтовый ящик. Реальная ценность
libp2p сводится к **стеку прохождения NAT**. Цена — вес: у проекта идеология
одного бинарника, а libp2p тянет сотни модулей и известен ломающими изменениями API.

| Этап | Чем | Почему |
|---|---|---|
| M0–M1: прямое соединение | **stdlib**: TLS 1.3 с закреплёнными публичными ключами поверх TCP | ноль новых зависимостей для безопасности; достаточно для узлов с прямой доступностью |
| M2: прохождение NAT | свой hole punching на STUN и нашем координаторе **или** libp2p | к этому моменту будет видно, насколько плох свой вариант |
| позже | QUIC, если понадобится | одна точечная зависимость |

**Критерий пересмотра прямой**: если доля успешных прямых соединений окажется
низкой, переходим на libp2p; замена локальна благодаря интерфейсу транспорта.

**Эскиз публичного API библиотеки** (умышленно узкий, без привязки к прикладной
задаче):

```
Identity:  Generate() / Load() / Fingerprint()
Contacts:  CreateInvite() / AcceptInvite() / List() / Verify() / Revoke()
Network:   Join(bootstrap) / Leave() / Status()
Dial:      Connect(nodeID) -> Stream      // с учётом всех запасных путей
Listen:    Accept() -> (Stream, contact)  // только для доверенных
Mailbox:   Put(nodeID, blob) / Fetch()    // опционально
Coordinator: Enable(policy) / Disable()   // режим координатора
```

Прикладной продукт видит только `Stream` между двумя проверенными контактами и
ничего не знает о координаторах, NAT и DHT.

### D9a. Экономика координатора — решено 2026-09-23

Кто и зачем держит координатор, если за трафик платит он, а пользуются другие.

Мотивация есть и без денег: собственный координатор означает, что **твой узел
всегда доступен** и ты не зависишь от чужих. Генеалогические общества и форумы —
естественные кандидаты на постоянные координаторы, это их обычная роль.

Затраты делаются предсказуемыми:

- **приоритет своим контактам**: им реле без жёстких ограничений, посторонним —
  по остаточному принципу и с лимитом;
- **бюджет трафика**: «столько-то гигабайт в месяц» с автоматическим отключением
  реле при исчерпании — понятно домашнему пользователю и не требует следить;
- сигнализация и справочник дёшевы всегда; ограничивается только реле, где идут
  мегабайты.

**Оплата, токены и кредиты отвергнуты явно**: отдельная вселенная сложности и
регуляторных вопросов ради экономии нескольких гигабайт трафика.

**Локальный интерфейс управления.** Координатору нужен свой раздел управления,
доступный только владельцу узла и не выставленный в сеть: политики и приоритеты,
квоты и бюджет, учёт израсходованного трафика, список обслуженных сессий, журнал
отказов с причинами. Он смыкается со страницей состояния обмена
([exchange/operations.md](exchange/operations.md#диагностика-для-пользователя))
и с блокировками ([exchange/control.md](exchange/control.md)).

### D10. Эксплуатационные параметры

Начальные значения для настройки, все — предмет уточнения на практике.

| Параметр | Начальное значение |
|---|---|
| Число домашних координаторов | 2–3 |
| TTL записи доступности | 15–30 минут, обновление вдвое чаще |
| Эпоха токена встречи | сутки, с перекрытием на границе |
| TTL заявки на встречу | 5–10 минут |
| Порог стажа для роли координатора | несколько часов непрерывной работы |
| Квота реле | лимит скорости и суммарного объёма на сессию |
| TTL почтового ящика | 24–72 часа, лимит объёма на отправителя |

### D11. Модель угроз (сводка)

| Угроза | Механизм противодействия |
|---|---|
| Подмена карточки при передаче | сверка отпечатка людьми по независимому каналу (U6) |
| Соединение от незнакомца | проверка ключа по списку доверенных до передачи данных (U8) |
| Вредоносный координатор читает трафик | сквозное шифрование между узлами (D1) |
| Вредоносный координатор подделывает записи | подписи и монотонный `seq` (D2) |
| Eclipse: изоляция новичка | несколько источников координаторов, защита кэша (D5) |
| Sybil: массовое создание координаторов | требования стажа и подтверждённой доступности (C7/C8), приоритет проверенным |
| Утечка метаданных (кто и когда в сети) | токены встречи (D6), приватный режим по умолчанию |
| Злоупотребление реле | квоты и лимиты (C11) |
| Отказ координатора в обслуживании | несколько домашних координаторов, быстрая замена |

## 4. Этапность внедрения

| Этап | Содержание | Результат |
|---|---|---|
| M0 | Идентичность, рукопожатие, соединение по известному адресу | два узла соединяются вручную |
| M1 | Координатор: сессии, справочник, сведение; клиентский bootstrap и кэш | соединение по NodeID в публичном режиме |
| M2 | NAT traversal: probe, hole punching, реле | работает за домашними маршрутизаторами |
| M3 | Приглашения, сверка отпечатков, списки доверенных | взаимное согласие как обязательное условие |
| M4 | Токены встречи, приватный режим по умолчанию | минимизация метаданных |
| M5 | Автопродвижение в координаторы, gossip | сеть живёт без исходных seed-узлов |
| M6 | Почтовый ящик, DHT | асинхронность и масштаб |

Сеть становится жизнеспособной после M3; M4–M6 добавляются по мере необходимости.

## 5. Открытые вопросы

Все вопросы этого раздела закрыты в ходе проходов F9, F12 и F17 (2026-09-23).

1. ~~**Несколько устройств одного пользователя.**~~ Решено: общая идентичность
   пользователя с подчинёнными ключами устройств; в поездку едет только ключ
   устройства — [exchange/identity.md](exchange/identity.md#идентичность-два-уровня-ключей).
2. ~~**Групповые связи.**~~ Решено: соединение «многие ко многим» не нужно.
   Группа — локальная выборка партнёров без сетевой семантики, а данные расходятся
   транзитом с подписью автора на каждой записи —
   [exchange/groups.md](exchange/groups.md).
3. ~~**Публичный режим.**~~ Решено отказом: узел **не отвечает на запросы от
   незнакомых ключей** вне процедуры знакомства — по приглашению или через точку
   интереса. Взаимное согласие остаётся строго обязательным.
4. ~~**Экономика координаторов.**~~ Решено: приоритет своим контактам, бюджет
   трафика с автоотключением реле, никаких оплат и токенов — см. D9a.
5. ~~**Подтверждение доставки и упорядочивание.**~~ Решено: обмен построен на
   запросе подписчика по курсору (pull), отдельного механизма подтверждения не
   требуется — [exchange/subscriptions.md](exchange/subscriptions.md#кто-кого-спрашивает).

Отложено намеренно: **публичная карточка входа** — статическая ссылка «точка
входа в сообщество», которую можно опубликовать на форуме или сайте. Устроена как
карточка контакта без одноразового секрета: ключ плюс координаторы, многоразовая.
Эпохи токенов ей не мешают, потому что ссылка ведёт на узел, а не на токен, и узел
сообщает актуальные параметры сам. Требует лимитов и ручного подтверждения каждого
новичка, поэтому вынесена в дальние задачи —
[exchange/discovery.md](exchange/discovery.md#отложено-публичная-карточка-входа).
