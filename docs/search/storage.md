# Индекс и очередь индексации

> Часть раздела [Поиск по базе](index.md). Подпроект P2.

## Выбор устройства индекса

Рассматривались три варианта:

| | A: лемма в постинге | B: формы отдельно | FTS5 поверх лемм |
|---|---|---|---|
| устройство | `postings(lemma, entity, field)` | `forms` + `form_lemma` + `postings(form, entity, field)` | виртуальная таблица FTS5 |
| поиск | лемма → постинги | лемма → формы → постинги (+1 join по маленькой таблице) | `MATCH` |
| точность «та же форма / та же лемма» | не видна без повторной токенизации | видна | не видна |
| исправление ошибочного разбора | переразбор текстов с этой леммой | правка `form_lemma` одной формы | полная перестройка |
| фрагменты | токенизация текста при показе | так же | `snippet()` покажет леммы, всё равно пересчитывать |

FTS5 (он включён в `modernc.org/sqlite`) даёт меньше, чем кажется: морфология и
нечёткость всё равно свои, фрагменты всё равно считаются по оригиналу, а ранжирование
`bm25` — число без доводов.

**Принят A′** — вариант A плюс id исходной формы в постинге. Поиск идёт прямо по
лемме, без join; точность формы видна; ошибочный разбор исправляется точечно.
Цена — одно целое на строку постинга и маленькая таблица форм.

## Схема

```sql
-- поверхностные формы, встреченные в базе (после орфографии), — не словарь языка
search_forms   (id INTEGER PRIMARY KEY, form TEXT NOT NULL UNIQUE)
-- леммы, встреченные в базе (включая псевдолеммы неизвестных слов)
search_lemmas  (id INTEGER PRIMARY KEY, lemma TEXT NOT NULL UNIQUE)

search_postings (
    lemma_id     INTEGER NOT NULL,
    form_id      INTEGER NOT NULL,
    entity_table TEXT    NOT NULL,
    entity_id    TEXT    NOT NULL,
    field        TEXT    NOT NULL,   -- имя поля; класс поля выводится в коде
    tf           INTEGER NOT NULL,   -- сколько раз форма встретилась в поле
    flags        INTEGER NOT NULL,   -- ambiguous | predicted | unknown | abbrev
    PRIMARY KEY (lemma_id, form_id, entity_table, entity_id, field)
)
-- индексы: (form_id) — сверка; (entity_table, entity_id) — удаление и переиндексация

-- рёбра подъёма и связей — см. ranking.md и filters.md
search_link (from_table, from_id, to_table, to_id, kind)

-- очередь заданий индексации
search_queue (id, kind, entity_table, entity_id, enqueued_at, attempts, last_error)

-- версии: правил нормализации, набора словарей
search_meta (key, value)
```

- Строка постинга — на пару (форма, лемма) в поле сущности, **без позиций**. У формы
  с двумя леммами — две строки с признаком `ambiguous`.
- Префикс по мере ввода — диапазон по `search_forms.form` (уникальный индекс).
  Инфикс и «похожие» — по `search_forms`/`search_lemmas`: это лексика базы, десятки
  тысяч строк, их можно держать в памяти.
- Флаг `private` в постинг **не копируется**: приватность проверяется join-ом по
  таблице сущности, как сейчас. Иначе смена приватности требовала бы переиндексации.

### Какие поля индексируются

Класс поля участвует в ранжировании ([ranking.md](ranking.md#ранжирование)):
**И** — идентифицирующее, **А** — атрибут, **Т** — тело текста, **П** — пометка.

| Сущность | И | А | Т | П |
|---|---|---|---|---|
| `Person` | фамилия, имя, отчество, приставка/суффикс имени, прозвища | сословия, титулы | — | `Notes`, `SourceLink.Note` |
| `Family` | название | — | — | `Notes` |
| `AdministrativeDivision` | название, варианты, прежние названия | — | — | `Notes` |
| `Parish`, `Church` | название (+ варианты у церкви) | текст `Settlements`, `Parish`/`Church` | — | `Notes` |
| `Repository` | название | адрес | — | `Notes` |
| `Archive` | название | — | — | `Notes` |
| `ArchiveNode` | метка, название | текст `Parish`, `Settlements` | — | `Notes` |
| `ArchiveDocument` | заголовок | вид, текст `Parish`, `Settlements` | — | `Notes` |
| `Source` | заголовок | автор | — | `Notes` |
| `Citation` | — | — | текст | примечание |
| `Note` | заголовок | — | текст | — |
| `Attachment` | имя файла | — | — | примечание |
| `Event` | — | текст места | — | `Notes`, примечания участников |
| `Relation`, `Residence` | — | — | — | `Notes` / примечание |
| словари (`Surname`, `GivenName`, `Patronymic`, `Estate`, `Title`) | каноническая форма, варианты | — | — | `Notes` |

Список — данные в коде рядом с индексатором каждого типа, с тестом соответствия
(каждый тип, у которого есть текстовые поля, имеет запись). Описания поиска в
MCP, справке и плейсхолдерах обязаны совпадать с этим списком буквально — правило из
[entity-write.md](../data-model/entity-write.md) сохраняется.

## Очередь индексации

- `Save*` и `Delete*` в `sqlstore` пишут задание в `search_queue` **в той же
  транзакции**, что и изменение данных. Индекс строит фоновый воркер.
- Виды заданий: индексировать сущность; удалить сущность из индекса; сверка после
  смены словарей; пересборка словаря, сгенерированного из базы; полная
  переиндексация.
- Задания по одной сущности схлопываются (последнее состояние читается из базы).
  Обработка идемпотентна; порядок — по `id`, поэтому сверка не гоняется с новыми
  записями.
- Ошибка задания не отбрасывается молча: `attempts`, `last_error`, повтор с
  нарастающей паузой, видимый счётчик «не проиндексировано N» (принцип «никакого
  молчаливого отбрасывания» из [operations](../exchange/operations.md)).
- Индексация сущности пересчитывает и её постинги, и её рёбра `search_link`.

**Следствия асинхронности:**

- запись находится через секунды после сохранения, не мгновенно;
- хит на уже удалённую сущность тихо отбрасывается при подгрузке (как «хит-гонка»
  в S16);
- переезд подчинённой сущности (заметка перепривязана к другой персоне) — обычное
  задание переиндексации.

## Сверка и переиндексация

**Сверка при смене набора словарей** (версия в `search_meta` не совпала):

1. пройти по `search_forms`, пересчитать леммы каждой формы текущим набором;
2. сравнить с леммами этой формы в постингах и применить разницу:
   - лемма сменилась → `UPDATE search_postings SET lemma_id = new WHERE form_id = F AND lemma_id = old`;
   - появилась вторая лемма → `INSERT … SELECT` по строкам формы `F` с новой леммой;
   - лемма ушла → `DELETE`;
   - флаги пересчитываются там же;
3. записать новую версию.

Тексты не перечитываются; работа пропорциональна лексике базы, а не объёму текстов.
Слово, бывшее неизвестным, получает лемму, как только его узнаёт словарь.

**Полная переиндексация** (`genodex reindex`) нужна только при смене правил
орфографии или токенизации — меняются сами формы. Версия правил хранится в
`search_meta`; несовпадение при старте ставит полную переиндексацию в очередь.

## Бэкап, восстановление, проверка

- Индекс — часть базы и по умолчанию бэкапится.
- `genodex backup --no-index` исключает таблицы `search_*` (для уменьшения размера);
  после `restore` без индекса полная переиндексация ставится в очередь автоматически.
- `genodex verify` сверяет выборку сущностей: пересчитанные постинги и рёбра равны
  сохранённым; очередь не содержит застрявших заданий.

## Перевод поисков по типам

Все `<entity>_search` (MCP) и `/api/<entities>/search` переводятся на новый движок
**без смены контракта**: тот же URL и ответ, внутри — глобальный поиск с фильтром по
типу и пресетом «Строго» ([ui.md](ui.md#пресеты)). Пикеры и списки получают
морфологию, орфографию и варианты.

После перевода удаляются таблица `search_index`, индекс `idx_search_term`,
`Store.Search` и `replaceSearchIndex`. Данные на этапе разработки
перестраиваются из сущностей — миграции содержимого нет.

## Минусы и меры

| Минус | Мера |
|---|---|
| самые ценные слова (фамилии, деревни) часто неизвестны словарю | предсказанная лемма с пониженным весом; словари из записей базы; «добавить в словарь» ([normalization](normalization.md#неизвестные-слова)) |
| омонимия имён и обычных слов, многозначные сокращения | набор словарей по полю; признак `ambiguous` с понижением; заглавная буква — слабая подсказка; довод «неоднозначный разбор» в выдаче |
| индекс и словари расходятся во времени | версия набора словарей; сверка по формам в фоне |
| fuzzy gomorphy ищет по словарю языка, а не по базе | «похожие» по двум источникам: словари и лексика базы ([ranking](ranking.md#похожие)) |
| нет позиций — нет фразового поиска и близости слов | для навигации приемлемо; фраза проверяется при построении фрагмента для первых N; колонка позиций — расширение, не переделка |
| смена правил орфографии меняет формы | `genodex reindex`, версия правил в базе |
| осиротевшие формы и леммы после удалений | периодическая чистка, не срочно |
