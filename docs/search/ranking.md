# Подъём к главной сущности и ранжирование

> Часть раздела [Поиск по базе](index.md). Подпроекты P3 (глобальный поиск) и P6
> («похожие»).

## Главные и подчинённые сущности

Совпадение в заметке, цитате, событии или имени само по себе редко нужно как
результат: нужен **объект, к которому оно относится**. Поэтому типы делятся на
главные (показываются в выдаче как результат) и подчинённые (поднимаются к главным и
показываются внутри главной как довод с фрагментом).

Связи сущностей образуют **граф, а не дерево**: одна заметка может быть в `Notes`
нескольких сущностей, цитата принадлежит источнику и доказывает утверждения о
персонах, у события несколько участников. Подъём может дать несколько главных.

### Правила подъёма

| Где найдено | Поднимается к | Довод |
|---|---|---|
| `PersonName`, прозвище, сословие, титул персоны | `Person` | «имя: Кузнецов Иван Петрович» |
| текст внутри `Notes` (`TextRef`) любой сущности | сама эта сущность | «в пометке: …фрагмент…» |
| `Note` | все сущности, чьи `Notes` ссылаются на неё; ссылок нет — заметка сама главная | «в заметке «Заголовок»: …» |
| `Citation` (текст, примечание) | `Source`; **опция:** цели её `SourceLink` | «в цитате из «Исповедная ведомость 1834»: …» |
| `Event` (место, пометки) | участники (`Person`); в доводе — ссылка на само событие | «событие: крещение, Покровское, 1834» |
| `Relation`, `Residence` | их персоны | «проживание: д. Давыдово» |
| `Attachment` | `ArchiveDocument`, иначе `ArchiveNode` | «вложение: …» |
| `Family`, места, архивы, узлы и документы архива, хранилища, источники | сами себя (главные) | — |
| словари | отдельный канал: словарный результат (ниже) | — |

- **Глубина — один шаг.** Единственный двухшаговый путь, **опция**: цитата →
  доказываемое событие → его участники. Иначе одна цитата из метрической книги
  поднимется к половине базы.
- Рёбра подъёма хранятся в `search_link` (вид `rise`) и поддерживаются очередью
  индексации ([storage.md](storage.md#очередь-индексации)).

### Несколько главных: порядок типов

В результат поднимается **одна** главная — первая по порядку типов. Остальные
показываются подсказкой **«также в: K, L, M»** в том же результате.

Порядок по умолчанию (задан в коде, переопределяется в настройках выдачи):

1. `Person`
2. `Family`
3. места: `AdministrativeDivision`, `Parish`, `Church`
4. `Source`
5. `ArchiveDocument`
6. `ArchiveNode`
7. `Archive`
8. `Repository`
9. `Note` (заметка без ссылок на неё)

**Ничья внутри типа** (заметка у трёх персон): выше та, у которой больше покрытие
слов запроса по собственным доводам; при равенстве — по id, чтобы выдача была
стабильной.

### Группировка — опция выдачи

- **включена:** один результат на главную сущность со всеми её доводами;
- **выключена:** один результат на совпадение, в заголовке — главная сущность.

Покрытие слов запроса считается **на уровне главной сущности**: для «Кузнецов
Покровское» фамилия совпала в имени персоны, а село — в её проживании, значит у
персоны полное совпадение.

### Путь по иерархии

Если главная сущность — часть иерархии, в подвале результата показывается путь:
губерния → уезд → волость; архив → фонд → опись → дело; цепочка родительских
заметок. Считается только для показываемых результатов, одним рекурсивным запросом.

## Словарные результаты

Словарная запись — **результат**: «Фамилия: Кузнецов» ведёт на запись словаря, а
внутри содержит группу действий:

| Словарь | Действия |
|---|---|
| фамилия | все персоны; все семьи; известные сочетания ФИО; варианты написания |
| имя, отчество | все персоны; варианты |
| сословие, титул | все персоны |

- Действие — готовый запрос: пустой текст, фильтр по словарной записи, тип
  ([filters.md](filters.md#комбинация-и-пустой-текст)). Отдельного кода для действий
  нет.
- **Известные сочетания ФИО** — производный результат, а не сущность: уникальные
  тройки (фамилия, имя, отчество) из `PersonName`, содержащие найденное слово, со
  ссылкой на список персон.
- **Виртуальный словарный результат.** Фамилия в `PersonName` — `TextRef` и может
  быть текстом без ссылки на словарь. Если слово встречается в именах, а записи
  словаря нет, показывается «Фамилия: Кузнецов (нет в словаре)» с теми же действиями
  и действием **«Добавить в словарь»** — точка пополнения и словарей базы, и
  тематических словарей gomorphy.
- В выдаче словарные результаты идут первыми.

## Приватность

Проверяется **на обоих концах подъёма**:

- публичная выдача скрывает приватную подчинённую сущность и приватную главную;
  если приватна только заметка, персона в публичном поиске по слову из этой заметки
  не находится;
- подсказки «также в…», пути по иерархии и словарные действия в публичной выдаче
  тоже не показывают приватного;
- владелец видит всё.

## Ранжирование

**Ступени, а не сумма весов.** Результат выше, потому что выиграл на первой ступени,
где различие есть. Каждая ступень объясняется доводом.

1. **Покрытие** — сколько слов запроса совпало на уровне главной сущности.
2. **Качество совпадения** — для каждого слова берётся лучшее, затем результаты
   сравниваются по худшему из слов:
   1. точная форма;
   2. та же лемма;
   3. вариант по словарю («Авдотья» ← «Евдокия»);
   4. предсказанная лемма;
   5. неоднозначный разбор;
   6. «похожее» (расстояние 1, затем 2).
3. **Класс поля** — идентифицирующее → атрибут → тело текста → пометка
   ([storage.md](storage.md#какие-поля-индексируются)).
4. **Прямота** — собственное поле → подъём на шаг → на два.
5. **Порядок типа**, затем id.

**Многословный запрос** — по множеству найденного это OR (в выдачу попадает всё, где
совпало хоть одно слово), по порядку — «сначала все слова»: частичные совпадения
ниже.

**Доводы** — показываются у результата списком: где найдено (поле, подчинённая
сущность), какой формой («нечётко: Кузнецво → Кузнецов», «вариант по словарю»,
«неоднозначный разбор»), фрагмент текста с подсветкой. Фрагмент строится повторной
токенизацией оригинала только для показываемых результатов.

## «Похожие»

Нечёткие совпадения — отдельный режим (P6), не смешиваются с точными:

- источники кандидатов: `FuzzyTop` по подключённым словарям gomorphy **и** по
  лексике базы (`search_forms`/`search_lemmas`) — иначе не найдутся фамилии, которых
  нет в словарях («Дарожкн» → «Дорожкин»);
- на странице результатов — отдельная секция, когда точных результатов меньше
  порога (по умолчанию 5, опция);
- в выпадающем списке — только при нуле точных, до 3, с пометкой.

## Контракты

Эскиз; окончательная форма — в плане P3.

**`GET /api/search`**

| Параметр | Смысл |
|---|---|
| `q` | текст запроса; может быть пустым при заданном фильтре |
| `type` | ограничение по типам главных сущностей (повторяемый) |
| `in` | фильтр-область: `<type>:<id>` (повторяемый, объединяются через И) |
| `preset` | `strict` / `normal` / `wide` |
| `opt.*` | переопределение отдельных опций пресета |
| `group` | группировка |
| `limit`, `offset` | окно |

Ответ — результаты (тип, id, подпись, путь по иерархии, доводы с фрагментами,
«также в…», действия у словарных), секция «похожие», счётчики по типам. Режим
доступа (`Access`) — из аутентификации запроса: владелец или публичный.

**MCP-тул `search`** — те же параметры и та же форма ответа; пресет по умолчанию
«Обычно». Как и прочие тулы, только чтение.

Существующие `<entity>_search` и `/api/<entities>/search` сохраняют контракт и
работают через тот же движок ([storage.md](storage.md#перевод-поисков-по-типам)).
