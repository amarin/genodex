# Приём данных: входящий ящик

> **Статус: обсуждение закрыто 2026-09-23, не реализовано.** Документ фиксирует
> итог задачи F4 — место, где сходятся решения всех остальных блоков раздела.
> Попутно закрыта часть [H8](requirements.md#h8-обмен-в-mcp-контуре) (ящик в MCP).

## Вопрос

Как человек разбирает входящий поток, как в интерфейсе уживаются свои и чужие
данные об одной персоне и что делать с объёмом: один срез по селу приносит тысячи
фактов.

## Что было решено раньше

- Входящий поток **не меняет базу напрямую**; всё проходит через решение человека.
- Приём **поштучный, на уровне факта**; пакетное допустимо там, где факт ни с чем
  не конфликтует ([identity](identity.md#приглашение-с-привязкой-и-вход-новичка)).
- Принятое — **замороженная копия**; обновление источника приходит уведомлением
  ([provenance](provenance.md#попутно-закрытые-вопросы)).
- Порядок и сворачивание предложений зависят от доверия к автору
  ([trust](trust.md#на-что-влияет-и-на-что-не-влияет)).
- Через этот же ящик проходят **конфликты правок между своими устройствами**
  ([identity](identity.md#несколько-устройств)).

## Лента — производная, а не источник истины

Записи приходят из разных мест, и состояние решения уже хранится в предметных
таблицах: `foreign_claim.status` для чужих фактов, `links.kind` для связей
тождества. Дублировать истину не нужно.

> **Лента ящика — производная таблица: порядок, прочитанность, отложенность,
> группировка. Источник истины — предметные таблицы. Ленту можно удалить и
> перестроить.**

Тот же приём, что с сайдкаром происхождения: данные лежат там, где им место, а
надстройка обслуживает подачу.

## Виды записей

| Вид | Откуда | Действия |
|---|---|---|
| новый факт | партнёр, файл | зеркало / принять / связать / отклонить |
| изменение принятого | источник поменял то, что я принял | принять новое / оставить своё |
| отзыв | автор отозвал ([revocation](revocation.md)) | снять пометку / удалить у себя |
| кандидат на сопоставление | [matching](matching.md) | связать / «это не тот же человек» |
| конфликт своих устройств | [identity](identity.md#несколько-устройств) | выбрать версию — **зеркала здесь нет** |
| поле неизвестного типа | другая версия программы ([wire-format](wire-format.md)) | сохранить непрозрачным, предложить обновиться |

Две последние строки ведут себя иначе остальных и не смешиваются с ними в общей
ленте: конфликт своих устройств — не «чужое предложение», а выбор между двумя
собственными правками.

## Три пути обработки предложения

| Путь | Что происходит | Когда уместен |
|---|---|---|
| **зеркало** | данные видны как «данные B», в мой граф не входят | «интересно, посмотрю позже» |
| **принять факт** | значение копируется в мою запись со ссылкой на источник | «его дата рождения с метрикой убедительнее моей» |
| **связать сущности** | моя и его записи связываются, чужие факты видны рядом | «это точно мой прадед» |

Плюс **отклонение** — с сохранением решения.

## Отклонение привязано к версии

Тонкость, которую легко упустить. Если отклонение привязать к факту, а не к его
версии, случится вот что: партнёр найдёт ошибку, исправит дату — и **исправление
не придёт**, потому что «вы уже отказались».

> Отклонение хранится по `(origin_user, FactRef, version)`. Новая версия — новое
> предложение.

Тот же принцип закрывает обратный случай: повторная доставка того же файла не
воскрешает отклонённое. А чтобы версией нельзя было злоупотребить, **сравнивается
содержимое, а не только версия**: если значение не изменилось, нового предложения
не возникает ([control](control.md#накрутка-версий)).

**Устаревание.** Если пришла более свежая версия того же факта, старое
предложение закрывается автоматически: человек не должен разбирать историю чужих
правок.

## Пакетное принятие: проверяемая формула

| Ситуация | Пакетно |
|---|---|
| факт создаёт новую сущность | да |
| факт заполняет пустое поле существующей сущности | да |
| факт расходится с имеющимся значением | **только поштучно** |
| факт совпадает с имеющимся | не предлагается вовсе |

Последняя строка экономит больше всего: при обмене с партнёром по общей ветке
совпадений будет большинство.

## Объём и релевантность

Партнёр прислал срез по селу: триста персон, из которых мои — пять. Остальные
двести девяносто пять — люди, которых я не исследую. Свалить всё в одну ленту
значит сделать ящик бесполезным в первый же день.

Разделение по релевантности — сначала факты о персонах, с которыми есть
совпадение, затем отдельный раздел «новые персоны» — требует результатов
сопоставления. То есть **ящик без [matching](matching.md) работает плохо**, и эту
зависимость лучше признать, чем обойти:

- **первая версия** (вместе с файловым обменом): группировка по пакету доставки
  и по сущности, порядок — по доверию к автору;
- **после F5**: раздел «похоже на ваших людей» и фильтры по релевантности.

## Отложить

Полноценное действие, а не украшение. Без него список не разгребается: человек
открывает ящик, видит сорок записей, по трети решения нет прямо сейчас — и
закрывает всё целиком. Отложенное уходит из основного списка, но решённым не
считается и возвращается по сроку или вручную.

## Отображение чужого рядом со своим

Карточка персоны должна показывать, что у партнёра другая дата рождения, не
превращаясь в таблицу разногласий. Требования:

- **чужое никогда не выглядит как моё** — прямое следствие главного принципа раздела;
- расхождение видно в контексте поля, а не только в ленте;
- у сокращённого факта виден признак «данные неполны по решению отправителя»
  ([privacy](privacy.md#состав-сокращённого-набора));
- у факта без подтверждённого авторства — признак «получено через посредника»
  ([wire-format](wire-format.md#две-подписи-авторство-и-доставка)).

## Обратимость

Любое решение откатывается: принял факт — снял, связал сущности — развязал.
Журнал решений — тот же `change_log` с `batch_id`, что обслуживает отмену пакетом
в разделе E ([provenance](provenance.md#журнал-изменений)).

## Общий механизм с помощниками ввода

Предложение от партнёра и предложение от разбора документа — одно и то же по
смыслу.

> **Таблица ленты, виды записей и интерфейс разбора — общие для раздела E
> (автоматизация ввода) и раздела F (обмен).**

Иначе получатся два похожих экрана с расходящимся поведением, а пользователь
будет гадать, почему «принять» в одном месте работает не так, как в другом.

## Ящик в MCP

Агент **читает** ленту и готовит сводку: сгруппировать, оценить, показать, что
важно. **Решения принимает только человек** — ни принятия, ни отклонения, ни
связывания сущностей у агента нет.

Это следует из главного принципа раздела: чужие данные входят в базу лишь по
решению владельца, а агент владельцем не является. Остальная часть
[H8](requirements.md#h8-обмен-в-mcp-контуре) — инициирование поиска и экспорт
через MCP — остаётся открытой.

## Итоговые требования

1. Лента ящика — производная таблица; источник истины в предметных таблицах; лента перестраивается.
2. Виды записей различаются; конфликты своих устройств и неизвестные поля не смешиваются с чужими предложениями.
3. Три пути обработки плюс отклонение с сохранением решения.
4. Отклонение хранится по `(origin_user, FactRef, version)`: новая версия создаёт новое предложение.
5. Более свежая версия автоматически закрывает устаревшее предложение.
6. Пакетное принятие — по формуле: новая сущность и пустое поле можно, расхождение только поштучно, совпадение не предлагается.
7. «Отложить» — полноценное действие с возвратом по сроку или вручную.
8. Первая версия группирует по пакету доставки и сущности; релевантность появляется после F5.
9. Чужое всегда визуально отличимо от своего; признаки сокращения и неподтверждённого авторства видны.
10. Любое решение обратимо; журнал общий с отменой пакетом (E4).
11. Лента, виды записей и интерфейс разбора общие для разделов E и F.
12. Агент в MCP читает ленту и готовит сводку; решения принимает только человек.

## Что осталось открытым

- Сроки и правила возврата отложенного.
- Как показывать длинную историю правок одного факта, если партнёр правит часто.
- Нужны ли уведомления вне ящика (значок, письмо) и при каких событиях.
- Предельный размер ленты и поведение при импорте очень большого среза: резать на
  части или показывать постранично.
