# Группы партнёров

> **Статус: обсуждение закрыто 2026-09-23, не реализовано.** Документ фиксирует
> итог задачи F17 (дыра [H7](requirements.md#h7-групповой-обмен)).

## Вопрос

Пять исследователей одной фамилии работают по общей ветке. Нужна ли для этого
сущность «группа» с сетевой семантикой, или достаточно попарных связей.

## Для распространения данных группа не нужна

Транзит разрешён (решение 3), а после F3 авторство переживает пересылку — подпись
стоит на каждой записи ([wire-format](wire-format.md#две-подписи-авторство-и-доставка)).
Данные и так расходятся по кругу: A отдал B, B отдал C, и у C сохранилась подпись
A. Дубликаты гасятся идемпотентностью по `(origin_user, FactRef, version)`.

Значит, группа решает не задачу доставки, а задачу **выбора людей**.

## Группа — локальное понятие

> **Группа — сохранённая выборка партнёров в моей базе. Сетевой семантики у неё
> нет: партнёры о ней не знают, общего состояния не существует, согласовывать
> нечего.**

Отсюда следствия:

- **групп может быть много**: по общему предку в определённом узле дерева, по
  точке интереса, по региону, по архиву — сколько удобно;
- выборка бывает **статической** (список, собранный руками) и **динамической**
  (правило: «все, с кем есть пересечение по селу Ивановка»);
- группа — часть моих данных, поэтому **едет на мои устройства** вместе со всем
  остальным ([identity](identity.md#несколько-устройств)), но никогда не уходит
  партнёрам;
- одного и того же человека можно держать в любом числе групп.

По сути это удобный способ не искать людей поодиночке каждый раз, а выбирать из
готового списка.

## Что отвергнуто

**Разделяемый объект** — общий список участников, реплицируемый между узлами.
Он требует распределённого управления членством: кто вправе добавлять и
исключать, что делать при конфликте «A добавил X, B исключил X», как упорядочить
эти события без общего времени. Это отдельная подсистема уровня всего раздела, и
ради круга из пяти родственников она несоразмерна.

**Групповая приватность** тоже отвергнута — раньше и по другой причине: групп с
разным объёмом выдачи не будет ([privacy](privacy.md#разные-правила-для-разных-партнёров)).
Членство в группе не даёт особых прав на данные.

## Массовые действия — отложены

Групповое действие в общем случае сводится к повтору: «сделать для A, повторить
для всех в группе Б». Городить механику раньше, чем появятся сами действия, смысла
нет, поэтому это отложено до момента, когда будет что повторять.

Отдельно отмечен сценарий, который повтором не описывается и потребует своей
механики: **запросить у всех и обработать индивидуальные ответы** — разослать
запрос по группе, собрать разные ответы, зарегистрировать каждый отдельно. Это
дальняя задача, но её стоит помнить при проектировании подписок.

## Итоговые требования

1. Группа — локальная сохранённая выборка партнёров; сетевой семантики нет.
2. Партнёры не знают о группах, в которые включены; общего состояния и согласования членства не существует.
3. Групп может быть много; выборка статическая или динамическая по правилу.
4. Группа принадлежит моим данным: синхронизируется с моими устройствами, партнёрам не передаётся.
5. Членство в группе не влияет на объём отдачи данных.
6. Массовые действия откладываются до появления самих действий; сценарий «запросить у всех и обработать ответы поодиночке» учитывается при проектировании подписок.
